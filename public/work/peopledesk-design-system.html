Design System · PeopleDesk v1.2

A design system for numbers
people have to trust.

PeopleDesk is a white-label HR, payroll and finance platform. Its system is built around one question: can the person running payroll tell, from the interface alone, what they are allowed to see, what will stop them, and what cannot be undone?

Context

Built while designing. Written down after.

I designed PeopleDesk end to end and built its component library in Figma as the screens took shape. The library worked, but its rules lived only in my head: why only one action earns a confirmation step, why one alert blocks a payroll run and another does not, why a hidden field shows a lock instead of a blank.

A white-label product is handed to teams that will never talk to its designer, so I turned that library into a documented system. This page walks through it the way a reseller's team would meet it: foundations first, then behaviour, then the components, then the rules that hold it together.

Every specimen below is live code built from the system's own tokens.

01Tokens

Three tiers. Ten values to rebrand.

Primitives hold raw values, semantic tokens give them a job, and component tokens scope that job to one element. Components may only reference the second and third tier. A hard-coded hex or a primitive inside a component is a review blocker.

One colour, three tiers
1 · Primitive--pd-violet-500

A raw value with no meaning attached. Owned by the system.

2 · Semantic--pd-action-primary

A role in the interface. The only tier a reseller may repoint.

3 · Component--pd-btn-primary-bg

Scoped to one component, so it can be retuned without touching the rest.

Repoint, don't repaint

A reseller swaps the ten --pd-violet-* primitives and the logo mark. Every action, focus ring and brand badge follows, including the translucent states, which are mixed from violet-500 instead of written as fixed values.

Status never moves

Green, amber, red and blue stay fixed in every tenant. In the preview the Ready and No hours badges keep their colour, because green has to mean success no matter whose logo is on top.

Named by job, not by pixel

The grammar is --pd-{family}-{role}-{variant}. --pd-status-critical-bg is readable without the file open. --pd-red-light-2 breaks the moment the hue changes.

02Color

Grey ground, white figures. Color never works alone.

The canvas is a cool grey and every unit of content sits on a white card, so each card reads as one object against the ground. Neutrals are cool greys, violet is kept for the primary action, the active state and links, and status colours always travel with an icon and a word.

Money is always tabular

Currency and counts use tabular-nums, right-aligned. The decimal points stack, so a scan down the column is enough to spot an outlier, and a changing digit never shifts the layout.

Large figures are tightened

Display and title sizes carry -0.02em tracking so a six-figure total reads as one number instead of a row of drifting digits.

04Spacing & Layout

4px base. Dense on purpose.

An 8px rhythm on a 4px base. The two smallest steps exist only for icon-to-label gaps and badge padding. Whitespace is spent separating groups, not padding individual items, because the people using this are operators, not visitors.

Tables reflow, they never scroll sideways

Below 1100px the payroll table becomes one card per employee. Horizontal scroll would hide the status column, which is the column that blocks a run.

Never truncate amount or status

Project and role may wrap. The amount and the status are the reason the table exists, so they are always shown in full.

Radius shows nesting

Tags 6px, controls 12px, blocks inside a card 14px, cards 20px, the workspace panel 28px. A child is always less round than its parent.

05Behaviour

Severity has consequences. Friction is spent once.

A problem's severity is defined by what happens if it is ignored, not by how serious it sounds. Each of the three severities maps to a different interaction, and only one action in the payroll flow earns a confirmation gate.

Resolve, review, consent, receipt

Only dispatching payroll and deleting an employee record cannot be undone. Both follow the same four steps, and nothing else in the product may use that shape.

Typing is the consent

The gate input has a dashed critical border so it never feels routine. The button stays disabled until the figure matches. The escape route is "Back to review", never "Cancel", so nothing entered is lost.

Motion confirms, never decorates

Five durations from 80 to 320ms. The slowest is reserved for the payroll success state, the one place a pause is wanted. Under reduced motion every duration collapses to zero.

06Permissions

Same record. Four outcomes.

The defining pattern of PeopleDesk. Permissions apply per field, not per page, so the same employee record renders differently for each role. Which outcome a field gets is a design decision, documented so it is never left to whoever writes the query.

Silence reads as broken

An empty panel tells a finance user the record is incomplete. A lock note tells them the data exists, who can see it, and that nothing is wrong.

Withheld or omitted is a design call

Withhold when the role may know the field exists. Omit when it may not. The consultant never learns that compensation or reviews exist on this record.

The lens is always on screen

Every record header says which role it is being viewed as. A user with more than one role should know which lens they are looking through before they act on what they see.

08In the product

Where the system shows up.

The same tokens and components, assembled. The payroll dashboard leans on tabular numerals, status badges and the resolver. The employee record is where the permission outcomes and the lens live.

09Voice

A competent colleague. Never cheerful about money.

Microcopy is part of the system, with the same do and don't treatment as a component. Name the person and the problem in the same line. Say what succeeded before what failed. No exclamation marks anywhere in the payroll domain.

10Principles

The rules behind the system.

Four rules settle most arguments in this product. When a component decision is contested, the earlier principle wins.

01

Severity is structural, not decorative

Every status pairs a hue with an icon and a label, and each severity maps to a different consequence. No fourth severity without a behaviour of its own.

02

Friction is spent, not spread

The product is fast everywhere except where an action cannot be undone. Adding confirmation to a reversible action devalues the gate that matters.

03

Permission is visible, not silent

When a role cannot see a field, the product says so. A user should understand that data is withheld, not wonder whether the record is incomplete.

04

Density serves the operator

Row height, type size and spacing are tuned for scanning, not comfort. Whitespace separates groups instead of padding individual items.

Deliberately left out. No dark theme yet: every token is named by role, so one can be added by remapping the semantic tier, but a second mode doubles what has to be tested before anyone has asked for it. No custom icon set: Lucide outline, with reserved meanings, so the lock always means withheld by permission and never "secure".

What this page does not claim. PeopleDesk was built to be resold, so there is no adoption or reuse data behind this system yet. With a reseller shipping on it, I would track hard-coded values introduced instead of tokens, and how long a rebrand takes against the ten values it should touch.
